## 1. SAM module configuration reference (COMPLETED)

### 1.1 SAM discovery normalization rules & publisher handling

#### 1.1.1 Normalization rules priority & structure
- **Rule order:** Lower integer = higher priority. Evaluate rules sequentially for each discovery.
- **Conditions:** name, version, publisher, edition, category, custom attributes.
- **Auto-create:** `glide.sam.normalization.auto_create_model` enables new model creation when no match.

**Publisher normalization critical:** Raw publisher strings (e.g., "Microsoft Corp", "Adobe Systems Incorporated") are mapped via `cmdb_sam_publisher_normalization` to standardized publisher records before matching.

**Undeclared identifier risk:** When publisher normalization fails, raw string used, usually resulting in no model match.

#### 1.1.2 SAM normalization for software discovery

The SAM module provides two core objects that drive discovery matching:

1. **Normalization Rules** — conditions that define the criteria for matching discovered software installations to Software Models.
2. **Publisher Normalization** — maps raw discovered publisher names to standardized publisher records.

Software Models serve as the target catalog. They define the product name, version, manufacturer, edition, and other attributes for normalization.

**Two distinct priority mechanisms:**

- **Normalization Rule priority:** via the `Order` field in `cmdb_sam_norm_rule`. Lower values = higher priority (evaluated first).
- **CMDB reconciliation priority:** via `reconciliation_order` in `cmdb_ci_reconcile`. Controls *whether* a CI record may be created/updated, separate from *which* Software Model is matched.

**Key separation:** Normalization answers "which Software Model"; IRE reconciliation answers "whether this source may write to the CI". A correctly normalized installation from a low-priority source can still be denied the CI update.

#### 1.1.3 Verification via normalization simulator

> "Normalization Simulator — Test normalization rules against sample data before applying them to production."

The simulator runs the real normalization logic against constructed installation data and reports which Software Model (if any) would be matched, without writing to production.

### 1.2 SAM configuration objects overview

#### 1.2.1 Core SAM tables

| Table | Purpose |
|-------|---------|
| `cmdb_sam_sw_model` | Software Model definition (name, version, publisher, edition, category) |
| `cmdb_sam_sw_install` | Discovered software installations (link to Software Model via `model_id`) |
| `cmdb_sam_publisher_normalization` | Publisher mapping from raw to standard names |

#### 1.2.2 Supporting CMDB integration

- **`cmdb_ci_spkg`** — Software Package CI (SAM's parent CI for software packages)
- **`cmdb_ci_app`** — Application CI (SAM's parent CI for applications)

#### 1.2.3 Configuration properties

Key SAM configuration properties:

- `glide.sam.normalization.enabled` — Enables/disables SAM normalization engine
- `glide.sam.normalization.auto_create_model` — Auto-creation flag for Software Models
- `glide.sam.reconciliation.enabled` — Enables/disables SAM reconciliation
- `glide.sam.publisher_normalization.enabled` — Enables/disables publisher normalization
- `glide.sam.normalization.simulator.enabled` — Enables/disables normalization simulator

### 1.3 SAM configuration best practices

#### 1.3.1 Rule design

- **Avoid overlapping rules:** Overlapping conditions between rules cause ambiguity; pick one side.
- **Create strong, specific rules:** Use precise conditions rather than broad catch-all.
- **Order carefully:** Test rule interactions before production deployment.
- **Include publisher normalization:** Always normalize publishers before evaluation.

#### 1.3.2 Integration design

- **Separate normalization and reconciliation:** Keep concerns distinct, use rule order for normalization priority.
- **Test with simulator:** Use normalization simulator to validate rule sets against realistic data.
- **Monitor publisher mapping:** Track publisher normalization effectiveness and map failures.

#### 1.3.3 Operations

- **Schedule regular publisher updates:** Maintain current publisher normalization data.
- **Monitor unmatched discoveries:** Review unmatched installations for manual investigation.
- **Document normalization strategy:** Keep clear documentation of normalization rules and logic.

## 2. Integration with existing Discovery/Discovery

### 2.1 Discovery process unchanged, results enhanced

Discovery sources (SCCM, Intune, etc.) submit installation data to `cmdb_sam_sw_install`. SAM normalization matches to Software Models, leaving underlying CI processing to the existing CMDB reconciliation layer.

### 2.2 CI parentage relationships

- **Software Package discovery** → `cmdb_ci_spkg` → `cmdb_sam_sw_install`
- **Application discovery** → `cmdb_ci_app` → `cmdb_sam_sw_install`

### 2.3 Cross-system references

SAM enables Discovery data to be displayed in existing CMDB reports while maintaining separation of concerns:

- Discovery continues to create `cmdb_ci_spkg`/`cmdb_ci_app` records
- SAM adds the Software Model reference (`model_id`) on `cmdb_sam_sw_install`
- Existing CMDB scripts can join these tables for comprehensive software asset reporting

## 3. Migration and deployment considerations

### 3.1 Staging environment setup

1. **Copy production normalization rules to staging**
2. **Test publisher normalization mappings**
3. **Validate auto-create behavior**
4. **Test reconciliation interactions**

### 3.2 Production deployment

1. **Begin with read-only mode:** Set `glide.sam.normalization.enabled = false`
2. **Enable normalization:** Set `glide.sam.normalization.enabled = true`
3. **Enable reconciliation:** Set `glide.sam.reconciliation.enabled = true`
4. **Monitor and refine:** Review unmatched discoveries and adjust rules accordingly

### 3.3 Rollback procedures

- Maintain backups of normalization rules and publisher mappings
- Document the state when changes were made
- Have clear rollback instructions for failed deployments

## 4. Troubleshooting guide

### 4.1 Common issues and solutions

#### 4.1.1 No Software Model match found

**Symptoms:** Installation records show null `model_id` after normalization.

**Causes:**
- Publisher not normalized
- Rule conditions not matching installation attributes
- Publisher normalization disabled

**Solutions:**
1. Verify publisher exists in `cmdb_sam_publisher_normalization`
2. Check rule conditions match installation attributes
3. Ensure normalization enabled

#### 4.1.2 Multiple installations mapped to same Software Model

**Symptoms:** Multiple installations with same `model_id`.

**Solution:** Review rule priority and conditions for specificity.

#### 4.1.3 New Software Models not being created when auto-create enabled

**Symptoms:** Installation records not linked to any Software Model and no new models created.

**Solution:** Check that `glide.sam.normalization.auto_create_model = true`.

### 4.2 Diagnostic queries

#### 4.2.1 Unmatched installations

```sql
SELECT swi.name, swi.version, swi.publisher, swi.category
FROM cmdb_sam_sw_install swi
LEFT JOIN cmdb_sam_sw_model model ON swi.model_id = model.sys_id
WHERE model.sys_id IS NULL;
```

#### 4.2.2 Publisher normalization failures

```sql
SELECT raw_name, normalized_name
FROM cmdb_sam_publisher_normalization
WHERE raw_name = 'Unknown Publisher';
```

### 4.3 Reporting

#### 4.3.1 SAM health report

```sql
-- Generate SAM health dashboard data
SELECT
  COUNT(DISTINCT swi.sys_id) AS total_installations,
  COUNT(DISTINCT model.sys_id) AS matched_installations,
  COUNT(DISTINCT CASE WHEN model.sys_id IS NULL THEN swi.sys_id END) AS unmatched_installations,
  COUNT(DISTINCT CASE WHEN model.sys_id IS NULL THEN NULL END) AS pending_creation
FROM cmdb_sam_sw_install swi
LEFT JOIN cmdb_sam_sw_model model ON swi.model_id = model.sys_id;
```
